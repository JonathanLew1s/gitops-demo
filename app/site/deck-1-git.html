Part 1 · Git

A commit is a snapshot with a name tag

Each commit stores

  • the snapshot of the files
  • author, time, message
  • the hash of its parent

Why security cares

The hash covers the parent's hash, so history cannot be quietly edited. Change one old commit and every hash after it changes.

In the VM worldA spreadsheet saved as rules_v7.xlsx, but every version kept, labelled, and impossible to quietly alter.
SAY: the 7-character codes under each dot are the hash. Real ones are longer, these are illustrative. Press → to build the chain commit by commit.

Your first commit, for real

Part 1 · Git · Two people, one file

What happens when two people change the same line?

Ana, on her branch

Changes the number of copies from 3 to 4: "peak traffic needs the headroom".

Ben, on his branch

Changes the same line from 3 to 2: "save cost, traffic is quiet".

Ana's change merges first

Git cannot tell whose change should win. It stops and asks a human. That stop is a conflict.

In the VM worldTwo engineers edit the same config on the same server at the same time. Whoever saves last silently wins, and nobody knows a decision was lost.
SAY: a conflict is not an error, it is Git refusing to guess. Different lines merge on their own; the same line needs a person. POINT: this is the "3 copies or 2" discussion you had in the last session, with the decision made visible.
Part 1 · Git · Reading a conflict

How Git shows you the disagreement

config/shop.yaml
image: registry.example.com/shop:1.4.1
<<<<<<< fewer-copies
replicas: 2
=======
replicas: 4
>>>>>>> main
resources:

Top: your version

What your branch says.

The line of equals splits them

Everything above is yours, everything below is theirs.

Bottom: what is already in main

The change that merged first.

A person chooses: keep one, keep the other, or write a new value. Delete the markers, save. The decision is a commit, recorded with who and why.

Not a failure: the file is simply showing both sides so you can decide. GitHub offers a "Resolve conflicts" button that does this in the browser, with no installs.

Worktree: two branches, two folders, one repo

~/gitops-demo

branch main

The application repo.

~/talos-gitops-demo

branch codex/gitops-demo-rollouts

A second checkout of the platform repo, so a platform fix never mixes with other work in progress.

One shared history

Both folders use the same .git store. Commits made in either are visible to both. No stashing, no half-finished edits to juggle.

Used for real during the building of this demo: one session, two repos, parallel pull requests.

SAY: you do not need worktrees on day one. They matter when you juggle several urgent changes: one folder per piece of work. SHOW: `git worktree list` in the terminal.

Cheat sheet

CommandPlain English
git statusWhat has changed since the last commit?
git add / git commitChoose edits, then save them as a named snapshot
git branch / git switchStart or move between safe drafts
git push / git pullShare my work / get everyone else's
git log / git diffThe history, and exactly what changed
