The audit question

Who changed it? When? Why? And can we get back to how it was on Tuesday?

With Git

Every change is recorded with its author, time and reason, forever, and any earlier state can be restored in seconds.

SAY: Git was built for source code, but it is really a tamper-evident log of changes to any text. Infrastructure is now text (YAML), so it applies directly. SECURITY ANGLE: "who, when, why" is the audit trail an auditor asks for. Git gives it by default.

How to read a change: red out, green in

firewall.rules
allow web-01 → db-01 port 5432
allow web-01 → cache-01 port 6379
allow web-01 → cache-01 port 6380
allow web-02 → db-01 port 5432

Red, with a minus: what was there before

The old value. It is being taken away.

Green, with a plus: what is there now

The new value. Red then green means the line was changed: the web-to-cache connection moved from port 6379 to port 6380.

A green line on its own is something new

web-02 may now reach the database. Nothing was removed, something was added.

The plain lines did not change. A reviewer only reads the red and the green: that is the whole change, however big the file.

In the VM worldThe change request says "update the firewall". You find out what that meant by comparing two spreadsheets by eye, or after something breaks.
SAY: before anything else, learn to read this. Red is what was there. Green is what is there now. That is all a diff is. Press → once per card: the red line, the green line (a changed rule is a red line followed by a green line), then the lone green line (a new rule). WHY IT MATTERS: every review you do today is reading a diff. If you can read this, you can review a change to production. ASK THE ROOM: "what changed here?" before pressing the last step.

What is Git?

A tool that remembers every version of your files: what changed, who changed it, when, and why.

firewall.rules
allow web-01 → db-01 port 5432
allow web-01 → cache-01 port 6379
allow web-01 → cache-01 port 6380
allow web-02 → db-01 port 5432

The label on that change

Who: an engineer
When: Tuesday, 14:02
Why: "Open DB access for the new web server; move cache off the old port"

Written by the person making the change, kept with it forever.

Snapshots, not surveillance

Git doesn't watch you type. You choose when to save a snapshot (a commit).

Differences on demand

It compares two snapshots and shows exactly what changed, line by line. Red out, green in.

Nothing is lost

Every earlier snapshot is still there. Go back to how it was last Tuesday in seconds.

In the VM worldWord's "Track Changes", but for any file, the whole folder, kept forever, and impossible to quietly rewrite.
SAY: forget the jargon for a minute. Git is "Track Changes" for a whole folder. You decide when to take a snapshot; Git can then show you the difference between any two. Press → once: the red and green lines are the change. Press again: the label (who, when, why) travels with it. Press again: the three ideas to remember. Git keeps the history. GitHub puts rules, robots and connections around it.

Actions: robots on every change

Check your standards. Catch a secret or personal data before it is saved. Build the new image. Run tests, scans, deployments.

Audit: every step recorded

Each change, approval, comment and permission change is logged and searchable.

Integrations: tools that react

Chat, ticketing, scanners and the platform itself plug in and respond to changes.

Control: who may change what

Required approvals, protected branches, rules nobody can quietly bypass.

In the VM worldSomeone logs into the test server (which everyone pretends matches prod) and clicks Next, Next, Next through the installer, hoping for the same result as dev. Here the steps run as code, every time: different people, same outcome.
SAY: Git is the notebook. GitHub is the office around it: the robots, the minutes, the plug-ins and the rules. THE POINT: people vary, they get tired, they miss things. A process plus automation takes that variation out of the result. OPTIONAL HINT (do not go deep): checks can also run on your own machine before you even push (pre-commit). BUILD IS A SLIDE ONLY: this demo has no image build; the checks you will see are standards and secrets.
