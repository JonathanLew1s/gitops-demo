Reading the dashboard: two questions

1. Does it match git?

Synced running what git says

OutOfSync git and cluster differ (a change is pending, or someone edited by hand)

2. Is it working?

Healthy all copies up, checks passing   Progressing rolling out now

Degraded something is wrong, with the reason attached

Two independent answers. "Synced but Degraded" means we shipped exactly what we meant to, and it is broken.

SAY: this is the one view an on-call person needs. Match and health are separate questions, and git can only fix the first.
Part 4 · LIVE Drift

Someone edits production by hand…

$ kubectl -n gitops-demo scale deployment web --replicas=5 # a well-meaning quick fix
# watch the pod tiles: 5 appear…
# Argo CD: OutOfSync. Git says 2. Self-heal kicks in…
# …and the count returns to what git says.

The lesson

A hand edit doesn't survive. If a change matters, it must go through git, where it is reviewed and recorded. Production can't quietly drift from the record.

Part 4 · What happens when it breaks?

Failure is normal. The design expects it.

What breaksWhat happens
A pod crashesReplaced within seconds. With 2+ copies nobody notices.
A server diesIts pods restart on other servers. The cluster heals itself.
A bad change is mergedNew copies fail their health checks, so old ones keep serving. Fix: revert the commit.
A canary fails its testsThe rollout aborts automatically. Users stay on the old version.
Argo CD is downEverything keeps running. Only changes pause until it returns.
GitHub is downSame: running apps are unaffected. We just can't ship for a while.
Someone edits prod by handReverted automatically, and visible as drift.
The whole cluster is lostRebuild from git. Data comes back from backups. That is why we back up.
In the VM worldHypervisor HA restarting your VMs elsewhere, extended to the whole application and its configuration.
SAY: the control plane is separate from the workload. Argo or GitHub being down is an inconvenience, not an outage. ASK THE ROOM: which of these rows would be a P1 incident for you today?
Part 4 · For the security team

Approved, visible, controlled

Approved

Every change is a pull request. Required checks, required reviewer, and the author can't approve their own.

Least privilege

People don't hold production credentials. The platform applies approved changes, and its reach is limited to one namespace.

Visible

The components table on the lesson page shows what is running and its scan status. Out of date is red, patched is green.

Reversible

Rollback is a reviewed commit. Disaster recovery is "rebuild from git, restore the data".

SAY: the point for security is not a new tool, it is that the control is in the workflow. You can't skip the review, because the review is how it deploys.

Part 4 · To take away

Three ideas to remember

1. Write down what you want

Infrastructure and its operations are text, in git, reviewed like anything else.

2. Let a loop make it true

A platform that continuously closes the gap between wanted and actual.

3. Change is boring, on purpose

Small, approved, reversible, with no downtime. That is the goal.

You don't have to adopt any of it tomorrow. Pick one small, boring thing and put it in git.
