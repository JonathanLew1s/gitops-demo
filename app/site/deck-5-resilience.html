Upgrades without downtime

Resilience by design, and a release process that tests itself on a small share of users before anyone else.

Part 5 · LIVE Resilience

One copy is a single point of failure

# Right now: one copy of the backend. The availability bar is green.
$ kubectl delete pod --force # a crash, no warning
# the bar turns red: about 12 seconds with no answer while the new copy warms up
# the fix is a reviewed pull request: replicas 1 → 2
$ kubectl delete pod --force # crash again…
# …nothing visible. The other copy kept answering.

1 copy

A crash is an outage until the replacement is ready.

2 copies

A crash is a non-event. Nobody is paged.

In the VM worldA single VM with no HA pair: a reboot, or a host failure, is an outage. Two VMs behind a load balancer is the same fix.
SAY: look at the green bar. Now watch it. After step 2, point at the red blocks and say how long they lasted. After step 5: the same crash, no red. REHEARSED NUMBERS: 1 copy about 12s outage (16 of 83 requests failed); 2 copies, 0 failures in 3 runs. IF ASKED why a normal delete shows nothing: a graceful delete lets the old copy keep answering while the new one starts. A crash gets no such grace.
Part 5 · Safe upgrades

A canary: try it on a few users first

  1. 100% oldeveryone on v1start
  2. 50% / 50%new version alongside the oldthe canary
  3. Tests runautomatically, on the new copieshealth, ready, serving
  4. A person looksand decidespromote or stop
  5. 100% newold copies retireddone

In the VM worldA phased roll-out across a server pool, with a go/no-go meeting in the middle, normally a weekend of manual work.
SAY: this is the difference between "deploy and hope" and "deploy and know". The new version proves itself on a small share before it gets everyone.

Part 5 · LIVE When a release is bad

The platform stops it, then we undo it

# "v3": a release with a bug. About a third of requests fail.
# the manifest checks pass: they cannot know the software is faulty
# merge → canary starts → automatic tests see errors…
# ~20 seconds: RolloutAborted. Degraded. Everyone else stays on the good version.
$ git revert # the fix is an ordinary, reviewed commit
# ~20 seconds later: Healthy. The whole story is in the history.

Blast radius

A small share of users, for about 20 seconds. Not everyone, not for hours.

Rollback

Not a panic. A revert, with the same approvals and the same audit trail.

In the VM worldA failed change, then an emergency change to back it out, and a post-incident review to work out what happened.
SAY: the tests are the same ones we ran a minute ago. They failed this time, so the release never reached everyone. HONEST NUMBERS: during that window 4 of 282 requests failed in rehearsal (1.4%). That is the cost of testing on live traffic, and why the canary is small. KEY POINT: we made the test strict. By default the tool tolerates a few errors in a row, and an intermittent bug slipped through our first attempt. That is a real lesson about writing the checks, not just having them.

Recap · how a change reaches production

The one-slide refresher

1. A change is a text edit

On a branch. Nobody logs into a server.

2. Robots, then people

Automated checks run first. Two people who did not write it approve it.

3. Argo CD applies it

And keeps it that way: a hand edit is undone in seconds.

4. Kubernetes keeps copies running

One failure does not cause an outage.

5. Releases go out a little at a time

Tested by robots. A rollback is another reviewed commit.
