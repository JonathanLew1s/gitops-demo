What is Kubernetes?

A pool of servers that runs your applications for you.

Many machines, one pool

The servers behind this page are four ordinary machines. Kubernetes treats them as one.

You hand it applications

It decides which machine runs each one. You do not pick a server.

It keeps them running

If a copy fails, it starts another. If a machine dies, the work moves.

In the VM worldYou request a VM, size it, install the application, patch it, and own that server for years. Here you say what you want, and the pool works out where and how.
SAY: not a product to learn today, an idea to recognise. A pool of machines that you describe work to, instead of logging into one. BRIDGE: the next slide is the single most important one.

Declare what you want. Don't do the steps.

Legacy: do the steps

Log in to the server. Stop the service. Copy files. Edit the config. Start it. Hope.

"It works if you do it in the right order, and Dave is the one who knows the order."

Modern: declare the result

"I want 3 copies of version 2, with this much memory."

A controller compares that to reality, every few seconds, and fixes any difference.

Like a thermostat. You set 21°. You never decide when the heating turns on. That is the whole of Kubernetes, and of GitOps.
SAY: this is the single most important slide. Everything after it is detail. "Desired state" versus "actual state", and a loop that closes the gap. INFRASTRUCTURE AS CODE: the description of what we want is a text file. OPERATIONS AS CODE: the procedures too (upgrade, rollback, scale, restore) become changes to that file.

Five words you will hear

Cluster

The whole pool of servers working together.

Node

One server in the pool.

Pod

One running copy of an application.

Replica

How many copies you asked for.

Namespace

A named area for one team's things, with its own budget.

Each of these comes back later, with something to see.

One line each. Do not stop to explain: the live look at the cluster, next, shows every one of them.
