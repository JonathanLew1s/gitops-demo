A team of tireless operators. You tell them what you want. They make it true, and keep it true.

Part 3 · The big idea

Declare what you want. Don't do the steps.

Legacy: do the steps

Log in to the server. Stop the service. Copy files. Edit the config. Start it. Hope.

"It works if you do it in the right order, and Dave is the one who knows the order."

Modern: declare the result

"I want 3 copies of version 2, with this much memory."

A controller compares that to reality, every few seconds, and fixes any difference.

Like a thermostat. You set 21°. You never decide when the heating turns on. That is the whole of Kubernetes, and of GitOps.
SAY: this is the single most important slide. Everything after it is detail. "Desired state" versus "actual state", and a loop that closes the gap. INFRASTRUCTURE AS CODE: the description of what we want is a text file. OPERATIONS AS CODE: the procedures too (upgrade, rollback, scale, restore) become changes to that file.

Part 3 · The building blocks

Pod: one running copy of an app

Container

The app plus everything it needs, sealed in one package. It runs the same on a laptop, in test and in production.

Pod

A running container (or two that work together). The smallest thing Kubernetes runs.

Disposable, by design

A sick pod is not repaired. It is replaced. We treat them as cattle, not pets.

On this site: the tiles at the top of the lesson page are real pods. Each name is a different running copy.
SAY: "cattle not pets" is the mindset shift in two words. Nobody logs in to fix a pod; it is just replaced with a fresh one.

Part 3 · The building blocks

Secrets: passwords are not config

Settings

Which colour, which message, how many copies. Fine to read in git.

Secrets

Passwords, keys, tokens. Never in git as plain text.

Three common ways to keep them safe

  • Encrypt before committing. The encrypted file lives in git; only the cluster can open it. (What this homelab uses.)
  • Fetch from a vault. The app asks a secrets vault at runtime. Nothing is stored in git at all.
  • Tight access rules. Only named people and systems may read a secret, and every read is logged.
Heads up: by default a Kubernetes Secret is encoded, not encrypted. Anyone allowed to read it can decode it in one command. So who may read is the real control.
SAY: this one is for the security team. The model is: no secret in plain text in git, tight RBAC, and encryption at rest and in transit. OPTIONAL LIVE (30 seconds): create a fake secret in the demo namespace, decode it with base64 -d, delete it. Use a made-up value only.
